# CPanel 系统审查与整改说明

检查日期：2026-11-04。基线：面板 `c7f9e70`，Corade `79fb7be`。范围包括管理员后台、订阅与门户授权、数据库记账、节点发布和 Agent 应用链路。实施分支均为 `fix/audit-remediation-20261104`。

本次同时检查功能正确性和操作体验。下面的原因描述针对基线问题；整改代码已在本地分支实施，验证记录见 [整改记录](audit-remediation-2026-11-04.md)。没有向生产环境写入数据或部署。

优先级：P1 影响线上服务、授权或账务；P2 影响编辑可靠性、故障定位和主要工作流；P3 影响管理效率和理解成本。未发现需要另建支付系统、后台角色体系或历史监控曲线才能解决的问题，不扩大产品范围。

## 按优先级排列的问题

### 1. P1：保存节点草稿可能改变已发布服务

**原因与影响**：编辑配置和运行配置使用同一份节点数据；把已发布节点改成草稿后，运行节点查询及订阅范围可能立即变化。“保存草稿”因此可能成为线上变更，机器、端口和入口的修改尤其危险。

**整改**：新增 `node_drafts`，后台读取时叠加草稿，运行查询仍读取已发布数据。发布在事务内校验机器、端口和关联配置，原子替换运行字段、入口、版本和事件。恢复历史也只写草稿。发布冲突保留原服务和编辑内容。

**代码与验证**：`internal/store/node_drafts.go`、`resources.go`、迁移 `0025_node_drafts_and_snapshots.sql`；真实 PostgreSQL 覆盖跨机器、端口冲突、多入口、事件、订阅和完整快照恢复。

### 2. P1：流量额度没有完整参与运行授权，撤销与尾部记账边界不一致

**原因与影响**：后台显示用量不代表 Agent 用户集合已按额度过滤；反过来，撤销后直接拒收尾部上报会漏记已经发生的流量。

**整改**：将有效额度纳入订阅与运行用户授权；达额后发送成员变更，重置或增加额度后恢复。运行授权与可记账资格分开，保留符合账号、节点关联约束的延迟上报。按一致顺序锁用户，避免统计重算覆盖并发上报。门户仍能登录查看已用额度，显示不可用原因。

**代码与验证**：`entitlements.go`、`traffic_usage.go`、`control.go`、`portal_quota_postgres_test.go`；覆盖达额、超额尾报、暂停/到期、重置恢复及并发重算。

### 3. P1：缩短保留期可能降低当月已用流量

**原因与影响**：自然月额度由每日记录汇总，而清理任务可删除当月明细；随后重算会让已消费额度重新出现。导入数据也存在相同风险。

**整改**：清理历史时同时保护站点时区下的当前自然月原始及导入流量记录，不因配置较短保留天数而删除。跨月仍按原重置策略执行。

**代码与验证**：`history.go`、`traffic_usage.go`；测试清理前后用量一致、导入记录、时区及夏令时边界。

### 4. P1：配置已获取、已提交与内核已应用没有可靠区分

**原因与影响**：普通遥测携带版本不能证明转换、证书处理、用户加载、内核启动或重载成功；界面却可能显示已同步。重载失败、机器迁移及旧回执还会制造错误成功状态。

**整改**：新增经原认证传输的 `node.application` 事件，区分 received/applied/failed 和失败阶段。只有内核应用成功才能确认；失败保留原成功版本。旧版本结果不能覆盖新版本状态，迁移机器清空确认。界面显示“配置已提交，等待 Agent 应用”，等待时加快刷新并显示数据更新时间。

**关联修复**：验证实际 sing-box 重载时发现出站、默认出口及上游依赖更新问题，已在 Corade 同步修复，并用实际内核测试确认配置真正生效。

**代码与验证**：面板 `control.go`、Corade `internal/controlplane` 和 `internal/kernel/singbox`；详见 [应用确认契约](../docs/node-application-results.md)。迁移 `0031` 会把旧的不可信 applied 值移入 received，applied 重置为 0，等待新 Agent 真正确认。

### 5. P2：套餐默认有效期容易被忽略，停用套餐仍可能被新分配

**原因与影响**：字段存在但没有统一服务端分配语义；空到期值可能被当成永久，创建、编辑和更换套餐行为不一致。只依赖前端禁用选项也无法防并发停用。

**整改**：定义保持原期限、按套餐默认、自定义、长期有效四种模式；首次分配按默认天数计算，正常换套餐保留已有期限。显式选择才重算。服务端拒绝新分配停用或归档套餐，并锁定关联校验。编辑页展示预计日期与生效节点范围。

**代码与验证**：`user_entitlements.go`、用户创建/更新及套餐处理；覆盖默认、自定义、长期、首次绑定、正常换套餐和并发停用。

### 6. P2：会话过期会丢失长表单内容

**原因与影响**：401 直接卸载认证后的页面；节点多协议、证书和规则输入往往无法轻易重建。自动重发又可能重复提交。

**整改**：隐藏并设为 inert 的编辑树保留在内存；停止受保护请求，原管理员重新认证后继续编辑，由用户明确重试。换管理员则销毁前一人的编辑树。页面明确提醒不要刷新或关闭；不把表单和秘密写入 localStorage、sessionStorage 或 URL。

**代码与验证**：`web/src/App.tsx`、`auth.ts`、`api.ts`；组件测试和浏览器模拟 401→重登录→输入保持→手动重试。跨管理员隔离由组件测试覆盖。

### 7. P2：创建或发布响应丢失后重试可能重复执行

**原因与影响**：请求超时不代表服务端未完成；仅禁用按钮不能处理断网、响应丢失和跨请求并发。新建保存成功但发布失败时，重试还可能再次创建节点。

**整改**：同一输入意图使用稳定 `Idempotency-Key`；数据库原子认领，业务、审计、加密响应一起提交。相同请求重放原结果，键和内容不一致返回冲突。发布重试保留最初键和配置版本，轮询不得刷新意图；新建部分成功转入已有节点编辑页。

**代码示例**：

```ts
const intent = creationIntent(); // 在组件生命周期内保留
await api.post('/nodes', payload, { idempotencyKey: intent(payload) });
```

**验证**：真实 PostgreSQL 并发创建只产生一条记录；丢失响应重试返回相同 ID；缓存凭据响应使用加密存储；节点发布部分成功测试。缓存有效期为 7 天，超过窗口不能承诺无限期重放；刷新浏览器后的新表单属于新意图。

### 8. P2：多标签、多管理员编辑会静默覆盖配置

**原因与影响**：读取后直接 PATCH，没有原子版本条件。把更新时间当版本还会被心跳、用量和应用回执误触发。

**整改**：七类资源提供独立 `config_version`，设置按分区提供版本；数据和版本从同一读取快照返回。写入在事务锁下核对 `If-Match`，冲突返回 409 `EDIT_VERSION_CONFLICT`。心跳与记账等运行列不触发编辑冲突，草稿、入口和节点绑定变化会触发。前端保留输入并要求确认后重新读取；缺少版本时禁止新界面盲写。

```ts
await api.patch(`/nodes/${node.id}`, values, {
  configVersion: node.config_version,
});
```

**兼容说明**：现有旧客户端未带条件头仍可调用；新后台发送条件头。此阶段不能宣称任意第三方旧客户端都受版本保护。相同意图的重放先于版本核对，避免成功后的旧版本阻止安全重试。

### 9. P2：前一次升级成功可能挡住后续新版本升级

**原因与影响**：历史升级任务终态参与“是否允许升级”判断，导致曾经成功过的机器在出现更新版本后仍无可用入口。

**整改**：进行中任务独立限制操作；成功、失败和超时只作为历史结果，是否有更新继续按实际 Agent 与目标版本判断。保留等待下发、已下发、已确认、成功、失败和超时的区分。

**代码与验证**：`web/src/resourceModel.ts` 和恢复测试；覆盖上次成功但目标版本再次变化。

### 10. P2：通用错误缺少可关联的诊断证据

**原因与影响**：“服务暂时不可用”无法判断失败接口、时间和请求；panic 日志信息不足时，现场难以和服务日志对应。

**整改**：错误保留请求 ID、时间、HTTP 状态和错误码，提供复制诊断；错误通知可主动关闭，不在短时间内消失。服务端记录同一请求 ID、路由模板及 panic 栈，避免记录带订阅令牌或门户授权参数的原始 URL。

**代码与验证**：`middleware.go`、`response.go`、`ApiError`、`RequestFailure`；日志测试确认请求 ID 一致且不暴露 URL 凭据。共享控件只引用公开认证错误类型，避免把后台请求与演示业务模块带入公开脚本，构建后的嵌入资源检查覆盖这一边界。超时未收到响应时可能没有服务端请求 ID，界面不会伪造。

### 11. P2：历史记录不足以真正恢复配置，审计失败可能被忽略

**原因与影响**：只存节点 config 无法恢复旧入口、监听与当时共享路由/出站；依赖已修改后“回滚”并非旧状态。业务提交后忽略审计错误，会出现已成功修改却无可靠审计记录。

**整改**：每个新发布版本保存完整节点文档和解析后的依赖快照。独立版本历史页面提供脱敏比较，恢复为草稿，确认后再发布。为不改动其他节点，旧路由快照恢复到本节点并解除共享绑定，界面明确说明。早期不完整记录只允许查看。配置变更和审计同事务；审计 SQL 或编码失败会回滚业务及幂等结果。

**边界**：退出会话、发 TG 测试消息等不适合用数据库回滚假装撤销外部动作，保留其原有操作边界。审计异常不能使已发消息被误报成未发送，也不能使退出失效。

内存中的面板身份缓存和 Agent 会话清理也必须在数据库提交后执行，回滚不能遗留未持久化的身份或误踢 Agent。服务器版本的外部查询移到事务之前，避免慢网络持锁阻塞其他保存或心跳；这两类边界均有真实 PostgreSQL 故障/阻塞回归。

**代码与验证**：`node_drafts.go`、`NodeHistoryPage.tsx`、`admin_consistency.go`、`request_transaction.go`；覆盖完整依赖恢复、恢复冲突、字段脱敏、审计故障及事务锁顺序。

### 12. P2：访问 IP 搜索与分页不一致，中文审计搜索难找到结果

**原因与影响**：先分页用户再查 IP 会让无记录用户占页；服务端和客户端二次过滤口径不一致，导致命中项被隐藏、总数和当前页矛盾。用户看到的中文操作和底层英文 action 不一致。

**整改**：服务端对有 IP 的账号筛选、搜索、计数后再分页；统一支持 IP、节点、地区和运营商。移除客户端重复过滤，空页可恢复。中文审计操作使用与展示一致的标签搜索，支持完整名称及片段，计数和分页使用同一匹配条件。

**代码与验证**：`user_access_ips.go`、`usePagedResource`、`AuditPage.tsx`、`admin.go`；55 个无 IP 账号加跨页记录验证计数、搜索、角色、节点和地区一致。

### 13. P2：慢网络下“进入门户”可能被浏览器拦截

**原因与影响**：等待授权接口后再调用 window.open 已离开用户点击的同步调用栈，浏览器会视为弹窗。

**整改**：点击时同步打开占位页，取得授权后导航；失败显示可恢复状态并关闭或允许关闭占位页，避免空白页面。保留只读代入，不把授权放入日志或持久存储。

**代码与验证**：`ResourceListPage.tsx`、`Recovery.test.tsx`，覆盖慢响应、弹窗拦截和授权失败。

### 14. P3：关联资源只能靠记忆串联，绑定数量容易误当可用数量

**原因与影响**：账号→套餐→权限组→节点需要反复离开和搜索；绑定节点数没有说明草稿、停用及未发布状态，容易误判为什么订阅为空。权限组也容易被误解为后台管理员权限。

**整改**：关键关联可直接跳转完整编辑页；账号和套餐显示节点访问范围、绑定与已发布数量、不可用原因以及期限预览。明确权限组负责订阅节点范围。加载关联失败显示未知并允许重试，不用 0 替代失败。

**代码与验证**：`EntitlementContext.tsx`、`ResourcePages.tsx`；原有顶栏、完整编辑页面、紧凑服务器/节点布局和明暗主题保持。桌面与手机截图见 [浏览器证据](audit-2026-11-04/browser-results.json)。

## 最值得先做的五件事

1. **隔离节点草稿和运行配置**：先确保保存不会无意中中断服务。
2. **闭合额度、撤销、恢复与尾部记账链路**：让面板显示、订阅和 Agent 授权一致。
3. **保护当月计费依据**：保留设置不能改变已发生的消费。
4. **采用真实应用确认**：让“已应用”成为可验证事实，失败保留旧服务。
5. **建立可靠保存事务**：幂等、并发版本检查和审计一起落地，降低重复、覆盖及难以追责的问题。

这五项先于继续视觉微调；套餐期限、会话恢复、搜索与关联导航随后减少日常操作成本。上述工作已按这一顺序在本地分支实施。

## 验证与交付边界

单元及行为测试覆盖异常和并发；真实 PostgreSQL 用隔离 schema 验证事务及 SQL；浏览器使用演示数据和拦截接口验证显示与会话恢复，不向线上发送写操作。该证据不等同于 SG1 生产验收、所有真实网络环境或长期压力测试。

面板与 Agent 有协调契约变更，发布前应备份数据库，先升级面板、再升级测试 Agent，观察真实 received/applied/failed 后逐步推广。新迁移为增量迁移；回退二进制前需核对未发布草稿、版本快照及旧 Agent 确认语义，不能把删表当回退步骤。
